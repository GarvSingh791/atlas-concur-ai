# Phase Summary
Phase:      Phase 2 — Core Backend Development
Sub-Phase:  P2-T3 — Auth System (Identity Vertical Slice)
Date:       2026-06-07

## Objective
Implement the identity vertical slice that the auth system requires before its
Validate gate can be satisfied.  The database has no users table until this task
runs, so auth endpoints cannot exist without it.  The MASTER_EXECUTION_PLAN's
vertical-slice execution rule explicitly authorises pulling the P3-T1 identity
models, the first incremental Alembic migration, and a minimal identity seed
forward into P2-T3 alongside the auth machinery itself.

Concrete deliverables:
- ORM models for the five identity tables (organizations, users, roles,
  permissions, role_permissions).
- Resolution of all FKs deferred since P2-T1/P2-T2 (TenantMixin → organizations;
  AuthorshipMixin → users; audit_log.actor_id → users).
- The first incremental Alembic migration covering these six tables only.
- A minimal identity seed: one organization, three users, roles/permissions/
  role_permissions, all passwords hashed.
- Auth primitives in core/security.py: password hashing, JWT issuance/verification,
  and the get_current_user FastAPI dependency (authentication only — no RBAC).
- The three auth endpoints: POST /auth/login, POST /auth/refresh, GET /me.

## Work Completed

### Identity models (P3-T1 pull-forward)
- `Organization` — tenant root; `id`, `name`, `base_currency`, `created_at`,
  `updated_at`.  Composes `UUIDPrimaryKeyMixin + TimestampMixin` only (no
  TenantMixin — it *is* the tenant).
- `User` — `UUIDPrimaryKeyMixin + TimestampMixin`.  Columns: `organization_id`
  (FK → organizations), `name`, `email`, `role` (PG enum `user_role`: employee /
  manager / finance_admin), `department`, `manager_id` (self-referential FK →
  users, NULL = top-level), `status` (PG enum `user_status`: active / inactive,
  default active), `preferences` (JSONB), `password_hash` (TEXT NOT NULL — see
  deviation note below).  Table-level `UNIQUE(organization_id, email)`.
- `Role` — `UUIDPrimaryKeyMixin` only.  `key` (PG enum `role_key`), `description`.
- `Permission` — `UUIDPrimaryKeyMixin` only.  `key` (TEXT UNIQUE), `description`.
- `RolePermission` — no PK mixin.  `role_id`, `permission_id`, composite
  `PrimaryKeyConstraint(role_id, permission_id)`.
- Two Python enums: `RoleKey` and `UserStatus` (both `str, enum.Enum`).  `RoleKey`
  is reused for both `users.role` (PG type `user_role`) and `roles.key` (PG type
  `role_key`) — same labels, distinct PG type names.

### Deferred FK resolution
- `TenantMixin.organization_id` now carries `ForeignKey("organizations.id",
  ondelete="RESTRICT")`.
- `AuthorshipMixin.created_by` and `updated_by` now carry
  `ForeignKey("users.id", ondelete="SET NULL")`.
- `AuditLog.actor_id` now carries `ForeignKey("users.id", ondelete="SET NULL")`.
  Confirmed still append-only (no updated_at / version / deleted_at).

### First incremental Alembic migration
- Alembic initialized from scratch: `alembic.ini` (repo root), `env.py`,
  `script.py.mako`, `versions/` directory.
- `env.py` reads `DATABASE_URL` from `Settings.DATABASE_URL` (never hardcoded);
  normalizes to `+psycopg2` driver; passes the SQLAlchemy `URL` *object* (not
  `str(url)`) to `create_engine` to avoid password masking (see QA findings).
- Migration `0001_initial_identity.py` — hand-written DDL (not autogenerated):
  creates the three PG enum types with `create_type=False` + `.create(checkfirst=True)`
  (idempotent against a DB where scoped `create_all` already ran), then creates all
  six tables in FK-dependency order.  Downgrade drops tables in reverse order then
  drops enum types with `checkfirst=True`.  Applied and downgraded cleanly against a
  live pg16 instance.

### Minimal identity seed
- `database/seeds/identity_seed.py` — runnable as `python -m database.seeds.identity_seed`.
- Idempotent: guards on organization name; safe to run twice.
- Creates: Atlas Demo Corp (USD); employee / manager / finance_admin roles; 6
  provisional permissions (`expense.read.own`, `expense.create.own`,
  `expense.read.reports`, `approval.decide.reports`, `expense.read.org`,
  `policy.manage`) with representative role→permission mapping; three users
  (Alex Employee, Morgan Manager, Finley Admin) with `employee.manager_id →
  manager`; all passwords hashed via `hash_password(settings.SEED_DEFAULT_PASSWORD)`.

### Auth primitives — backend/app/core/security.py
- `hash_password(plaintext) → str` — bcrypt via the `bcrypt` library directly
  (`gensalt(rounds=PASSWORD_HASH_ROUNDS)` + `hashpw`).
- `verify_password(plaintext, hashed) → bool` — `bcrypt.checkpw`; never raises.
- `DUMMY_HASH` — precomputed at startup; used by the login service on the
  missing-user code path to maintain constant-time-ish behaviour (no user
  enumeration via timing).
- `create_access_token(user_id, org_id)` and `create_refresh_token(...)` —
  python-jose HS256-signed JWTs; claims: `sub`, `org`, `type`, `exp`, `iat`.
  Lifetimes from `Settings.ACCESS_TOKEN_EXPIRE_MINUTES` (15) /
  `REFRESH_TOKEN_EXPIRE_DAYS` (7).
- `decode_token(token, *, expected_type)` — verifies signature, expiry, and type
  claim; raises `UnauthorizedError` for any failure.
- `get_current_user` — FastAPI dependency via `HTTPBearer(auto_error=False)`.
  Extracts the bearer token, calls `decode_token(expected_type="access")` (rejects
  refresh tokens), loads the org-scoped user, rejects missing or inactive user.
  **Authenticates only — no role or permission check** (that is P2-T4).

### Identity module — backend/app/modules/identity/
- `schemas.py`: `LoginRequest`, `TokenResponse`, `RefreshRequest`,
  `AccessTokenResponse`, `MeResponse` (from_attributes=True; never includes
  `password_hash`).
- `service.py`: `login()` — always raises the same generic `UnauthorizedError`
  for unknown email AND wrong password (no enumeration); runs `verify_password`
  against `DUMMY_HASH` even when the user is not found.  `refresh_access_token()`.
- `router.py`: `POST /auth/login`, `POST /auth/refresh`, `GET /me`; mounted at
  the design-doc literal paths (no `/identity` prefix).
- Registered in `backend/app/api/v1.py` with `tags=["identity"]`.

### Tests
- `backend/tests/test_identity_auth.py` — 13 live-DB tests covering all Validate
  conditions: valid login returns tokens; /me returns correct user with no hash;
  wrong password and unknown email return identical 401; /me with no/malformed/
  expired/refresh token returns 401; refresh with valid refresh → new access; refresh
  with access token → 401; inactive user cannot authenticate.
- All tests self-skip when Postgres is unreachable (hermetic CI pattern from P2-T2).
- `backend/tests/test_audit.py` — updated for resolved FKs; scoped fixture now
  creates org + user so FK constraints are satisfied; test bodies reference real UUIDs.
- `backend/tests/test_db_conventions.py` — teardown fixed to use per-table `.drop()`
  instead of `metadata.drop_all` (avoids enum-type cascade errors on a migrated DB).

## Integration Points
- Auth reuses the P2-T1 shared engine/sessionmaker (`get_db` dependency) and the
  P2-T1 `Base` + composable mixins.
- All error paths use the P2-T2 `AppError` / `UnauthorizedError` hierarchy so
  failures return the standard error envelope.
- `get_current_user` is the authentication seam that P2-T4 (RBAC enforcement) will
  build on — it returns the authenticated `User` ORM object; P2-T4 wraps it with
  `require_permission` / `require_role` dependencies.
- `audit_log.organization_id` and `audit_log.actor_id` now resolve to real FK
  targets; existing `test_audit.py` fixture updated accordingly.
- The identity seed's `roles` / `permissions` / `role_permissions` rows are the
  data that P2-T4's RBAC checks will query.

## Technical Decisions

### Password hashing library
Used the `bcrypt` library directly (≥4.0, <6.0) rather than `passlib[bcrypt]`.
`passlib 1.7.4` + `bcrypt≥4.0` are incompatible: passlib's internal wrap-bug
detection routine hashes a >72-byte test password, which bcrypt 4+ rejects.
`bcrypt` has a stable, simple API (`gensalt` / `hashpw` / `checkpw`) and is
actively maintained.  `passlib[bcrypt]` was removed from `requirements.txt`.

### JWT library
Used `python-jose[cryptography]` (already pinned in requirements).  Algorithm
`HS256` (from `Settings.JWT_ALGORITHM`).  Claims: `sub` (str user UUID), `org`
(str organization UUID), `type` ("access" | "refresh"), `exp`, `iat`.  Both
access and refresh tokens are issued at login; only access tokens are accepted
by `get_current_user`; a refresh token presented as an access token is rejected
with a 401.  Access lifetime: 15 min.  Refresh lifetime: 7 days.  Both from
Settings; no hardcoded values.

### Incremental migration sequencing — documented adjustment
`MASTER_EXECUTION_PLAN.md` Section 5 lists a single all-tables migration as item
15 in the Phase 3 build order.  This task instead establishes a **per-slice
incremental migration** strategy: each vertical slice writes its own migration as
its tables are built.  This is explicitly authorized by the plan's
"Vertical-slice discipline" execution rule (model → migration → route → test per
entity).  **P3-T2 should be understood as "add the remaining domain tables" not
"create all tables from scratch."**  This decision is recorded here so the P3-T2
implementer knows the identity tables + audit_log are already present.

### Alembic initialization
Alembic was not present before this task (`database/migrations/` contained only
`.gitkeep`).  Initialized here with `alembic.ini` at the repo root pointing to
`database/migrations/` as the script location.  `env.py` reads `DATABASE_URL`
from `Settings` (no hardcoded URL in `alembic.ini`); passes the `URL` object
(not `str(url)`) to `create_engine` — `str(URL)` renders the password as `***`,
causing authentication failures.

### No user enumeration on login
The login service raises the same generic `UnauthorizedError("Invalid credentials.")`
for unknown email AND wrong password.  When the email is not found, `verify_password`
is still called against `DUMMY_HASH` to maintain timing behaviour indistinguishable
from a real wrong-password path.

### password_hash column — deviation from DATABASE_SCHEMA.md
`DATABASE_SCHEMA.md` defines no credential column on `users` and specifies no
`auth_credentials` table.  A stored hash is unavoidable for password-based login.
`password_hash TEXT NOT NULL` was added to `users` as the minimal, safe choice.
This is the sole authorized deviation from the schema doc; it is flagged in the
migration comment and the status report.  `password_hash` is never returned in
any response schema and never written to logs.

## Risks Identified
- **Incremental migration sequencing.** The MASTER_EXECUTION_PLAN's Section 5
  lists a single migration at item 15.  This task deliberately deviates to a
  per-slice strategy.  If P3-T2 is implemented without reading this log, the
  implementer may attempt to re-create tables that already exist.  Mitigation:
  this log is the record; P3-T2 must read it before touching migrations.
- **Refresh token revocation.** Issued refresh tokens cannot be invalidated
  without a token store (not built).  This is a deliberate future seam — any
  token valid at issuance can be used until expiry.  Mitigation: refresh tokens
  are 7 days; a token-store (Redis or DB) can be added in a later task without
  changing the token format.
- **Single-tenant email uniqueness at login.** The login service queries by
  email alone (not by organization_id).  In a multi-tenant deployment, two
  organizations could have a user with the same email and the first match would
  always win.  For the current single-tenant build this is safe; the unique
  constraint is per `(organization_id, email)` not globally.  Mitigation: when
  multi-tenant mode is switched on (NFR-S4), the login flow must accept an
  organization identifier alongside the email.

## Resolution Actions
- `passlib[bcrypt]` replaced with `bcrypt` directly to resolve the passlib 4.x
  incompatibility.
- `str(SQLAlchemy URL)` → URL object passed to `create_engine` in `env.py` to
  fix password masking.
- `datetime.UTC` (Python 3.11+) → `datetime.timezone.utc`; ruff rule UP017 added
  to `ignore` list in `pyproject.toml` since dev runtime is Python 3.10.
- Test fixtures refactored to use per-table `.drop(checkfirst=True)` instead of
  `metadata.drop_all` (avoids cascading enum-type drops on a migrated DB) and to
  prune stale test data at setup so repeated runs against a persistent DB are safe.
