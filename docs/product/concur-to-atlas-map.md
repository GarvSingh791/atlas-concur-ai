# Concur concepts mapped to Atlas

This page maps each publicly described SAP Concur concept to the part of Atlas that plays the same role, with the code path and what Atlas deliberately simplifies. For the overview, read the first two columns; engineers can follow the code paths (all relative to the repository root and checked against the code).

> [!IMPORTANT]
> Atlas is an independent engineering study inspired by SAP Concur. It is not affiliated with, authorized by, sponsored by, or endorsed by SAP SE or its affiliates. SAP and SAP Concur are trademarks or registered trademarks of SAP SE in Germany and other countries. All data in this project is synthetic.

The "Concur concept" column describes products only as their public material does (see the [domain study](domain-study-sap-concur.md) and its sources). It says nothing about how SAP implements them.

**Related:** [domain-study-sap-concur.md](domain-study-sap-concur.md) · [PRD.md](PRD.md) · [requirements-traceability.md](requirements-traceability.md) · [ARCHITECTURE.md](../ARCHITECTURE.md)

## At a glance

| Concur concept | Atlas equivalent | Main difference |
|---|---|---|
| Concur Travel | Conversational Travel Planner | Mock inventory, no ticketing |
| Concur Request / travel policy | Trip approval + planner policy checks | Approval after selection, not a separate request object |
| Concur Expense | Expense reports with smart match and pre-submit check | One policy, one org per login |
| ExpenseIt / Receipt Analysis Agent | Receipt pipeline with routed gap-fill | Vision OCR through an LLM provider or a local stub |
| Card feeds | Seeded card transactions + matching | Simulated feed |
| Audit rules / pre-submit audit | Deterministic policy engine (24 active rules) | Synthetic policy, no human audit service |
| Approval workflow | LLM-free approval agent + manager/finance queue | Single deciding approver, no delegates |
| Reimbursement | "Mark reimbursed" with a `REIMB-…` reference | No money moves |
| Joule-style assistant and agents | Orchestrator + agents + RAG policy assistant | Web app only, no Microsoft 365 surface |
| Analytics / Budget | Role-shaped dashboards and finance KPIs | Trip-level budgets only |
| User and role admin | Users admin, RBAC, traveller grades | Three fixed roles, no SSO |
| Audit trail | `audit_log` + `ai_decision_logs` | Append-only by convention |

## Concept map

| Concur concept | What it does (public description) | Atlas equivalent | Where in code | What Atlas does differently or simplifies |
|---|---|---|---|---|
| **Concur Travel** (booking) | Corporate booking of flights, hotels, rail and car with policy enforced in the booking flow | Travel Planner: free-text request → editable intent chips → one clarifying question → policy-checked, ranked flight and hotel options → select to create a draft trip | `ai_agents/agents/travel_agent/` (`intent.py`, `extraction.py`, `ranking.py`, `reflection.py`, `persistence.py`), `ai_agents/tools/inventory.py`, `services/mock_inventory/`, `backend/app/modules/travel/`, `frontend/app/(app)/planner/page.tsx` | **Simulated inventory**: a static seeded dataset plus synthetic generation, no GDS/NDC, no ticketing. Flights and hotels only. Ranking gives in-policy options a fixed +100, then adds price, sustainability (a 1–5 score) and preferred-supplier bonuses, so compliance outranks price |
| **Travel policy at point of sale** | Options tagged in or out of policy while shopping; out-of-policy choices may need justification or approval | Every planner option carries an in-policy / out-of-policy label, the reason and the clause codes; out-of-policy options are labelled, never hidden; planner notices for advance booking (PTA-02), lowest fare (AIR-06) and grade-based business class (AIR-04) | `ai_agents/tools/policy_eval.py`, `ai_agents/agents/travel_agent/ranking.py`, `ai_agents/agents/travel_agent/reflection.py`, `ai_agents/agents/process_checks.py` | One synthetic policy (Helios Dynamics TEP-FY26). An honesty critic checks that an out-of-policy option is never presented as compliant |
| **Concur Request** (pre-trip approval) | Estimate a trip and get it approved before booking | A trip moves `draft → pending_approval`, which opens an approval that the approval agent auto-approves or escalates; PTA-05 asks for re-approval when a trip's cost rises by more than 10% | `backend/app/modules/travel/service.py`, `backend/app/modules/approval/lifecycle.py` (`open_approval_on_submission`), `ai_agents/tools/process_rules.py` | No separate request object: the trip itself (with `estimated_cost` and an optional `budget_amount`) is what gets approved. No AI cost estimator |
| **Concur Expense** (expense report) | Turns spend events into reviewed, compliant, reimbursable reports | Expense reports: entries from receipts and card transactions, rule-first categorisation, hotel-folio itemisation, assembly into a draft report, pre-submit check, submit, withdraw, move lines between reports | `ai_agents/agents/expense_agent/` (`ingest.py`, `matching.py`, `categorize.py`, `assemble.py`, `presubmit.py`), `backend/app/modules/expense/`, `frontend/app/(app)/expenses/page.tsx` | Report states are `draft`, `submitted`, `approved`, `rejected`, `reimbursed`; a returned report goes back to `draft`. Mileage entries computed server-side (MIL-01..03) |
| **ExpenseIt / Receipt Analysis Agent** (receipt capture) | Turns a receipt photo into an expense line; the agent version infers missing fields from itinerary and calendar context, with routing and reflection | Receipt pipeline: OCR extracts six fields (`amount`, `currency`, `date`, `vendor`, `location`, `expense_type`) with per-field confidence; fields at confidence ≥ 0.70 stay deterministic; the rest go to an LLM gap-fill grounded in the itinerary and calendar (±1 day); a reflection step nulls a wrong inference; each field gets a provenance badge (`deterministic` / `ai_inferred` / `user_edited`); a draft expense is created in the Receipt Inbox | `ai_agents/receipt_pipeline/` (`core.py`, `gap_fill.py`, `reflection.py`, `pipeline.py`, `inbox.py`), `ai_agents/tools/itinerary_calendar.py`, `services/ocr_provider/`, `backend/app/modules/receipt/` | OCR is either a vision model via OpenRouter or a deterministic local stub. Image bytes are never sent to the gap-fill LLM. PDFs are rasterised to one image of their first 3 pages and never stored. Calendar events are seeded |
| **Card feed reconciliation** | Corporate card charges flow in and are matched to receipts and trips | Card transactions tab; smart match on amount, currency, normalised vendor and a date window (card ↔ receipt ±1 day; charge ↔ trip segment within the trip dates ±1 day); a receipt and the card charge for the same purchase become one entry; CARD-03 checks reconciliation timing | `backend/app/modules/card/`, `database/models/card_transaction.py`, `ai_agents/agents/expense_agent/matching.py`, `ai_agents/tools/process_rules.py` | **Simulated card feed**: transactions are seeded (`database/seeds/topup_demo_card_feed.py`), not received from an issuer. No real-time card-swipe expense creation |
| **Expense audit / policy compliance** (audit rules, pre-submit audit) | Configurable rules flag over-limit, missing-receipt, disallowed and duplicate items before or after submission | Deterministic policy engine: 24 active structured rules enforcing 29 clauses (air, lodging, meals, ground, entertainment, mileage, process); pre-submit flags with the clause and an explanation; justification for justifiable violations; unverifiable rules escalate instead of passing | `ai_agents/tools/policy_eval.py`, `ai_agents/tools/entry_rules.py`, `ai_agents/tools/process_rules.py`, `ai_agents/tools/fx_policy.py`, `ai_agents/tools/spend_policy.py`, `ai_agents/tools/grade_entitlements.py`, `ai_agents/agents/expense_agent/presubmit.py` | Rules only, no ML anomaly or fraud model and no human audit service. Duplicate and re-filed receipts are detected by lineage and receipt reuse checks |
| **AI-assisted rule authoring** | Admins create or change policy rules from natural language or policy documents (announced 2026) | Finance admin describes a rule in plain language → LLM drafts a structured rule → a critic validates it and round-trips it through the engine → saved as `draft` → a human activates it; per-rule change history | `ai_agents/agents/policy_authoring.py`, `backend/app/modules/policy/` (`router.py`, `history.py`), `frontend/app/(app)/policy/page.tsx` | Natural language only, not document upload. A drafted rule never becomes active without a human |
| **Approval workflow** | Reports and trips route to approvers with exceptions surfaced | Approval agent with **no LLM**: auto-approves only an in-policy trip or report with zero blocking flags, no required approver and a known total ≤ $500; never auto-rejects; otherwise routes to the submitter's manager. Queue ordered by status, blocking flags, then age; approve, reject with reason, or request changes; a human can reverse an auto-approval until reimbursement | `ai_agents/agents/approval_agent/` (`routing.py`, `evaluate.py`, `persistence.py`), `backend/app/modules/approval/`, `frontend/app/(app)/approvals/page.tsx` | One deciding approver, no multi-step chain. **No delegates**: when routing would reach nobody or the submitter, it falls back to a finance admin. Flags that need an SVP or VP route to an approver of that grade (`backend/app/modules/approval/grade_routing.py`) |
| **Segregation of duties** | Nobody approves or pays their own claim | Self-approval and self-reimbursement refused; the content a reviewer returned is frozen on the approval step; a re-filed returned or rejected claim escalates | `ai_agents/agents/approval_agent/evaluate.py`, `backend/app/modules/approval/`, `backend/app/modules/lifecycle/service.py` | Enforced in application code, covered by tests such as `backend/tests/test_pg_integ_lifecycle_sod_db.py` |
| **Reimbursement / payment** | Approved expenses are paid to the employee and posted to accounting | Finance "Ready to reimburse" queue and **Mark reimbursed**, generating `REIMB-<yyyymmdd>-<id>`; mixed-currency reports are reimbursed at the converted total | `backend/app/modules/lifecycle/` (`router.py`, `service.py`) | **Simulated reimbursement**: a state change and a reference, no payment and no ERP posting |
| **Multi-currency** | Foreign-currency spend converted for policy and totals | Foreign lines converted before caps and in totals; unsupported currencies flagged `currency_unverified` and escalated | `config/constants/fx_rates.py`, `ai_agents/tools/fx_policy.py`, `backend/app/modules/expense/fx.py` | **Static FX**: 11 currencies, labelled "simulated reference rates (not live market data)". Mileage is USD only |
| **Joule-style conversational assistant and agents** | A copilot that answers questions and hosts task agents (booking, receipt analysis, report automation, pre-submit audit) | An orchestrator with a rule-based classifier routes each task to the travel, expense, policy or approval handler; deterministic when confidence ≥ 0.75, agent + critic otherwise; policy Q&A over a hybrid RAG engine with clause citations or a calibrated abstention; replies sent as SSE frames | `ai_agents/orchestrator/` (`classifier.py`, `orchestrator.py`, `registry.py`), `ai_agents/agents/policy_qa.py`, `ai_agents/rag/`, `ai_agents/guardrails/`, `backend/app/modules/ai/`, `frontend/components/atlas/assistant/` | Four task routes, not an open agent platform. The assistant lives inside the Atlas web app only. Agents can only call actions on a fixed allow-list tied to the user's permissions (`ai_agents/guardrails/actions.py`). LLM provider is configurable (`LLM_PROVIDER`: `local`, `openrouter`, `anthropic`); staging uses OpenRouter → Gemini 2.5 Flash |
| **Analytics / Intelligence / Budget** | Consolidated, near-real-time spend reporting and budget views | Role-shaped dashboards; finance KPIs: Consolidated Spend, Automation Rate, Exception Rate, Avg Cycle Time (submitted → reimbursed), Avg Time to Decision, Budget Posture; department budget vs actual; CSV export of approvals and the audit log | `backend/app/modules/analytics/`, `frontend/app/(app)/analytics/page.tsx`, `frontend/app/(app)/dashboard/page.tsx` | Budgets are per trip (`trips.budget_amount`), not a separate budgeting product. No data warehouse; queries run on the operational database |
| **Team visibility** | Managers see their team's spend and activity | Team view: direct reports with open trips, reports by status, pending approvals, month-to-date and 90-day spend; drill-down per member | `backend/app/modules/team/`, `frontend/app/(app)/team/page.tsx` | One level of direct reports; finance sees everyone in the organisation |
| **User and role administration** | Admins manage users, roles and approvers | Users admin for finance: add, invite (one-time link), edit, deactivate / reactivate, set traveller grade; permission keys per role (`resource.action.scope`); account recovery (reset, invite, verification) | `backend/app/modules/identity/` (`admin.py`, `accounts.py`, `service.py`), `config/constants/permissions.py`, `config/constants/grades.py`, `backend/app/core/rbac.py`, `frontend/app/(app)/users/page.tsx` | Three roles (employee, manager, finance admin). No SSO, SAML or SCIM. Email delivery defaults to a `console` provider that sends nothing |
| **Audit trail** | Who did what, when and why, for compliance | Append-only `audit_log` for every business event, including refused admin actions; one `ai_decision_logs` row per AI task (route, provider, tool and output summaries, confidence, reflection outcome, correlation id), minimised for secrets and PII; filterable audit screen with CSV export | `backend/app/core/audit.py`, `backend/app/modules/audit/`, `database/models/audit_log.py`, `ai_agents/decision_log/`, `frontend/app/(app)/audit/page.tsx` | Append-only by convention, not enforced by the database. AI decision rows are stored but have no dedicated viewer |
| **Notifications** | Users are told when something needs their attention | Notification bell with unread count, mark read / mark all read, links to the subject | `backend/app/modules/notifications/` | In-app only; no push or email notifications |

## What Atlas does not model

These are real parts of the T&E domain that Atlas leaves out on purpose (see the PRD's [out-of-scope list](PRD.md#out-of-scope)):

| Concur concept | Why it is out |
|---|---|
| Live travel content and ticketing (GDS, NDC, direct connects) | Not available to an independent project; the planner uses mock inventory |
| Concur Invoice (accounts payable, purchase requests, three-way match) | A separate pillar from travel and expense |
| TripLink / TripIt (off-channel bookings, itinerary management) | Out of MVP focus |
| ERP and accounting posting (for example S/4HANA, NetSuite, QuickBooks) | Design seam only; reimbursement stops at a simulated state |
| Human audit services | Atlas audits with deterministic rules only |
| Duty of care and disruption handling | Not built |
| Native mobile apps | Atlas is a web app |
| Embedding in third-party copilots (for example Microsoft 365 Copilot) | The assistant is inside Atlas only |

For the list of what was built beyond the original spec (reimbursement, withdrawal, notifications, search, team view, card feed, FX, grade rules, account recovery, rate limiting, upload hardening, demo mode, PDF receipts), see [requirements-traceability.md](requirements-traceability.md#built-beyond-the-original-prd).
